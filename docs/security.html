FruitHub Security Guide

Current protections, their limits, and the configuration required before public launch.

← Documentation home · Owner handbook · Payment safety

Honest scope: this explains protections visible in the current application code. It is not a security certification or a guarantee that deployment infrastructure is secure. Before production, have the deployed system reviewed and configure secrets, HTTPS, database access, backups, and production SMS correctly.

1. Accounts, passwords, and sessions

  • Passwords are hashed using Argon2 through the application’s password hasher. The stored password is not the original password.
  • Login returns a signed JWT that expires based on ACCESS_TOKEN_EXPIRE_MINUTES (default: 60 minutes).
  • API requests use a bearer token; backend dependencies decode the token, load the active account, and check the required role.
  • Customer, owner, and admin APIs have role checks. Public registration creates a customer account; owners are provisioned by an admin.
  • Login uses a generic incorrect-email-or-password message to avoid revealing which part was wrong.
The frontend saves the access token in browser localStorage. This is convenient, but a successful cross-site scripting (XSS) attack could expose it. This project has not been documented as using an HttpOnly-cookie session. Use HTTPS, keep scripts/dependencies controlled, avoid shared/public computers, and sign out on devices you do not control.

2. Role and ownership boundaries

  • Owners’ product queries filter by the owner’s store. Owners should not be able to edit another owner’s products.
  • Owner order/payment operations filter by the owner’s store. Owner verification should not reach another store’s payment.
  • Customer order lookups filter by the authenticated customer, preventing one customer from accessing another customer’s order through the API.
  • These are server-side checks; hiding a button in the frontend is not considered authorization.

3. Phone verification and OTP safety

  • OTP codes are randomly generated, expire, and are stored as HMAC hashes using the application secret rather than as plain codes.
  • Old codes are consumed when a new code is sent. Resend and per-hour limits, expiry, and a maximum number of attempts are enforced.
  • Development defaults are not production-safe: OTP_DEV_MODE=true can return the OTP in the API response, and the console SMS provider prints it in the backend terminal.
  • No production SMS provider is configured in this project. Do not make real users rely on console output.

4. Input, upload, and storage protections

  • Request schemas validate types, lengths, ranges, and formats for important fields such as phone, password, prices, and UPI transaction references.
  • Image uploads are owner-authorized, limited by size (default 5 MB), accepted only for JPEG/PNG/WEBP, decoded as real images, and dimension-limited to help resist malformed or oversized image files.
  • Uploaded images are stored under generated names rather than the user-supplied filename. Local storage resolves paths and rejects keys that escape the configured uploads directory.
  • Database calls use SQLAlchemy query expressions/parameters rather than building queries by concatenating user text.

5. Request protections and response headers

  • Login, registration, and OTP endpoints have rate limits in the application.
  • CORS is configured from CORS_ORIGINS; production should list only the real frontend origin(s), not broad untrusted origins.
  • The backend adds X-Content-Type-Options: nosniff, X-Frame-Options: DENY, and Referrer-Policy: same-origin.
  • These headers and CORS do not replace HTTPS, a reverse proxy’s secure configuration, a content-security policy, or broader production hardening.

6. Required production configuration

  1. Set a long, randomly generated SECRET_KEY in the deployment secret manager. Never commit it, send it in chat, or reuse the development/test secret.
  2. Set OTP_DEV_MODE=false. Configure a real SMS provider only after choosing it and obtaining its credentials; store credentials in environment secrets, not source files.
  3. Use HTTPS for the website and API. Restrict CORS to the exact deployed frontend origins.
  4. Use a production database account with only required permissions. Keep connection strings secret. Back up the database and test restore procedures.
  5. Protect the uploads directory/storage, restrict server access, and consider durable object storage for multi-instance production deployments.
  6. Review production logging and monitoring so that passwords, access tokens, OTPs, payment references, and secret values are not exposed unnecessarily.
  7. Test rate limits, account recovery, order ownership, owner-store authorization, and payment paths on the actual deployment.

# Keep secret values private; this example intentionally contains no actual secrets.
SECRET_KEY=<generate-a-long-random-secret-in-your-secret-manager>
OTP_DEV_MODE=false
SMS_PROVIDER=<only-after-a-real-provider-is-implemented-and-configured>
CORS_ORIGINS=https://your-real-storefront.example

7. Security items not to overclaim

  • Direct UPI is not a verified gateway integration. A submitted UTR is user-provided text until the owner checks their bank/UPI account.
  • The configured payment provider in the current app defaults to a mock provider. Mock payment is only suitable for development/testing.
  • There is no configured production SMS provider, automated payment webhook, payment dispute service, or automatic direct-UPI refund.
  • Alembic migrations have to be applied safely to the intended database after a verified backup; generating SQL offline does not migrate a database.
  • Passing tests checks covered behavior, not every vulnerability or production infrastructure setting.
