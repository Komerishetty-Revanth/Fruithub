FruitHub Owner Handbook

How owner access, products, stock, visual previews, UPI, and order handling work in the current project.

← Documentation home · Security guide · Payment safety

Owner control: the owner controls their store profile, product data, inventory, product-photo previews, configured UPI ID, submitted-payment decisions, and the allowed order-status steps. Admin-only controls such as creating owners and approving stores are not owner controls.

1. What is in the current Owner panel

Open frontend/pages/owner.html (the header shows Owner panel for an owner account). Currently this screen lets an owner:

  • Set or update the store UPI ID used for customer direct payments.
  • See customer-submitted UPI references for that owner’s store.
  • Confirm money received or reject a reference. Confirmation should happen only after checking the actual UPI/bank account.
The current frontend does not provide a complete visual product-management dashboard for adding/editing products, managing all inventory, or handling every order. These operations exist as owner-protected API endpoints. Use the interactive API page at http://127.0.0.1:8000/docs while the backend is running, or build a dashboard UI for those actions. Do not expect a hidden product dashboard button that is not in the current code.

2. Who is allowed to be an owner

  • Public registration creates customer accounts, not owner accounts.
  • An admin must create/provision the owner account and make sure the store is approved and active.
  • Owner endpoints require a signed-in account with the OWNER role. Product, order, image, and payment operations are scoped to that owner’s store.
  • If you are a store owner but do not have an owner login, ask the FruitHub administrator to provision it. Do not edit database roles manually.

3. Add a product using the API page

  1. Start the backend and open http://127.0.0.1:8000/docs.
  2. Use POST /api/v1/auth/login with the owner’s own email/password. Copy the returned access_token privately.
  3. Click Authorize in Swagger and enter Bearer YOUR_ACCESS_TOKEN. Never paste the token into a public chat, document, screenshot, or issue.
  4. Use GET /api/v1/categories to find the category ID and category product type (FRUIT, JUICE, or DRY_FRUIT).
  5. Use POST /api/v1/owner/products with an example like this. Replace the placeholder category ID with a real category UUID and adjust information to the actual item:
{
  "name": "Fresh Orange Juice",
  "description": "Freshly prepared orange juice",
  "ingredients": "Orange",
  "allergens": null,
  "is_veg": true,
  "shelf_life_days": 1,
  "storage_note": "Keep refrigerated",
  "sugar_info": "No added sugar",
  "is_made_to_order": true,
  "category_id": "REPLACE-WITH-ACTUAL-CATEGORY-UUID",
  "price": 120,
  "discount_price": null,
  "unit": "bottle",
  "stock_quantity": 10,
  "is_available": true
}

Accepted units include kg, g, piece, dozen, ml, l, bottle, and pack. Whole-number units such as bottle/pack/piece require whole quantities. A discount price cannot exceed the regular price. Required food details depend on the product category and application validation.

4. Edit a product, update stock, or hide it

  • GET /api/v1/owner/products: list the current owner’s products and copy the product ID.
  • PATCH /api/v1/owner/products/{product_id}: change only the fields sent, such as name, description, category, price, discount, unit, or availability. Stock is deliberately changed through the stock endpoint.
  • POST /api/v1/owner/products/{product_id}/stock: add or remove quantity and provide a reason/note. The app records inventory history and prevents stock going below zero.
  • POST /api/v1/owner/products/{product_id}/deactivate: hide/deactivate a listing.
  • POST /api/v1/owner/products/{product_id}/activate: reactivate it.
  • GET /api/v1/owner/inventory: review stock-change history.

Use the endpoint’s Try it out panel in Swagger; it supplies path, body, and response examples. A missing ID or another store’s product should fail rather than granting access.

5. Upload and control a product animation

  1. Open the product’s public detail page while signed in as its owner.
  2. In Animated product view, choose Upload photo and regenerate. Use a clear JPG, PNG, or WEBP product image at least 300 pixels on each side and no more than 8000 pixels on a side. The configured upload limit is 5 MB.
  3. Image processing runs in the background. The image/preview may take a moment. Refresh the product detail page when processing is finished.
  4. Regenerate preview reprocesses the product’s current primary photo.
  5. Remove preview disables the generated preview. The product still has its product image; removing the animation is not the same as deleting the product.
  6. After generation, customers see the animated WebP preview in product cards/cart where used. Product detail loads an interactive photo-depth effect. Without a generated preview, still product photos are used.

The generated product visual is created from a cutout and depth map. It is not a true scanned or fully modelled 3D object. The product page lets the customer drag to tilt the depth effect and zoom; the cart animation is a small visual preview only. The home page also contains separate built-in Three.js product-type decorations.

6. Owner settings and UPI ID

  1. Open Owner panel and enter the actual VPA/UPI ID controlled by the store.
  2. Save the setting. Owner can update it later from the same panel.
  3. Without a saved UPI ID, customers cannot create a manual-UPI checkout for that store.
  4. The UPI ID must be correct: checkout creates a standard link for customers’ installed UPI applications and shows the payee/amount for confirmation.

Store location and delivery radius are administered separately and are not owner-editable through these store settings. The backend does not transfer money itself.

7. Verify, reject, and manage orders

  1. Owner panel shows references submitted for pending UPI payments belonging to this store.
  2. Before confirming, open the store’s trusted banking/UPI app independently and verify the actual credit and amount. A typed reference or screenshot is not verification.
  3. Confirm marks payment paid and makes the order available in the owner order list.
  4. Rejecting marks the payment failed, cancels that pending order, and restores stock. If money was actually credited, the owner must resolve/refund it outside FruitHub rather than assuming rejection refunds automatically.
  5. Owner can advance paid orders through permitted steps using POST /api/v1/owner/orders/{order_id}/status. Use GET /api/v1/owner/orders and its status filters in Swagger to inspect orders.
  6. For customer addresses outside the store’s delivery radius, the owner cannot mark the order “out for delivery.” The customer arranges and pays for external delivery separately and confirms receipt after ready.
Submitted UPI references reserve stock for a limited review period (up to 24 hours). If not resolved before expiry, the order is cancelled and the stock released. Tell the customer to contact the store promptly if a real transfer is delayed or pending.

8. Offer and category APIs

  • GET /api/v1/owner/offers, POST /api/v1/owner/offers, and corresponding PATCH/activate/deactivate routes support store offers.
  • POST /api/v1/owner/categories creates a category where permitted. Product-type/category governance and store approval can involve admin-controlled operations.
  • See API schemas directly in Swagger at /docs for exact request fields.

9. Owner safety checklist

  • Keep the owner password and bearer token private. Sign out on shared devices.
  • Use accurate prices, stock, ingredients/allergens, expiry, and storage details.
  • Use product photos you are permitted to publish and do not upload private customer documents.
  • Verify every direct UPI payment in your account. Never request PINs, OTPs, or passwords from customers.
  • Do not promise automatic refunds. Direct UPI refunds are outside the application.
  • Contact the admin for owner-account, approval, delivery-radius, or store-location changes.
